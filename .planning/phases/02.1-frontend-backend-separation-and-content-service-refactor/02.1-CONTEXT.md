# Phase 02.1: 前后端分离与内容服务化改造 - Context

**Gathered:** 2026-04-16
**Status:** Ready for execution planning
**Source:** 当前仓库审计、用户的“先备份再系统规划前后端分离”请求，以及对 Fastify / Vite 当前官方文档的 Context7 校验

<domain>
## Phase Boundary

本 phase 要解决的是架构边界，而不是继续往纯前端上堆内容：

- 把当前单体前端仓库演进为 `apps/web + apps/api + packages/quiz-core` 的轻量分离结构
- 让后端接管 canonical 题库与角色内容的运行时输出
- 让前端改为通过 API 读取内容，而不是直接导入 Markdown 真源
- 让 quiz 类型和匹配逻辑在前后端之间共享，避免再次出现双轨真相漂移
- 保持现有产品边界：无登录、无数据库、无 CMS、移动端优先、隐藏祥子规则不变

本 phase 不做：

- 账号系统、权限系统、数据库建模
- 后台内容管理台或在线题库编辑器
- 视觉大改版或结果页玩法重写
- Phase 3 的粉丝文案深化与角色校准本身

</domain>

<decisions>
## Implementation Decisions

### Locked

- 这次前后端分离采用单仓轻量 workspace，而不是多仓或微服务
- 目标目录固定为 `apps/web`、`apps/api`、`packages/quiz-core`
- 前端继续使用 React + TypeScript + Vite；后端采用 Fastify + TypeScript
- Fastify 选型已通过 Context7 查询当前官方文档校验：支持轻量 TypeScript server、插件注册与 schema-based route 定义，适合当前只读 JSON API 场景
- Vite 联调方式已通过 Context7 查询当前官方文档校验：开发态使用 `server.proxy`，客户端环境变量通过 `import.meta.env` 读取，并使用 `VITE_` 前缀
- 后端首阶段保持文件驱动和只读 API，不引入数据库、登录或后台管理台
- `questionedit/questionnewV2.md` 继续保留为编辑真源，但运行时 canonical 解析与序列化迁到后端
- 匹配算法继续保持可在客户端执行，以保留当前“本地答题、低延迟、无账号”的体验；后端在本 phase 只负责内容真源与 contract 输出
- 隐藏祥子的触发规则、公开榜首优先级和当前 V2.1D 算法语义必须保持一致

### The agent's Discretion

- workspace 具体脚本命名与 root/package 的组织细节
- `packages/quiz-core` 中 parser helper 与 DTO mapper 的精确边界
- API 路由拆分为单文件还是多模块，只要保持只读清晰即可
- 前端加载内容时使用轻量 data layer 还是在现有页面状态机内直接拉取
- 是否额外暴露 `version` / `etag` / `cache-control` 之类的轻量缓存元信息

</decisions>

<specifics>
## Specific Ideas

- 当前浏览器通过 `questionnewV2.md?raw` 直接参与 canonical 解析，这正是前后端边界最需要先切掉的部分
- `src/shared/types/quiz.ts` 和 `src/features/quiz-engine/model/match.ts` 已经足够接近共享 domain package，可以作为 `packages/quiz-core` 的起点
- `canonicalQuiz.ts` 里的 Markdown 解析逻辑更适合迁到 API 层，由后端启动时构建或按需缓存
- 前端改为拉取 `/api/quiz/content` 后，Phase 3 的题库和文案深化就可以只围绕内容真源与校验，不必再碰浏览器 raw import
- API 首批端点至少应覆盖：
  - `/api/health`
  - `/api/quiz/meta`
  - `/api/quiz/content`
- 如果后续要增加服务端评分或运营能力，`packages/quiz-core` 可以成为共用算法层；但这不是本 phase 的强制交付

</specifics>
