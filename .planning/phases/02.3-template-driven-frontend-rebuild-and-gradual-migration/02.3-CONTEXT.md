# Phase 02.3: 模板驱动的前端重构与渐进迁移 - Context

**Gathered:** 2026-04-22
**Status:** Ready for execution planning
**Source:** 用户关于“完全用新模板重构现有前端”的明确要求、当前 `apps/web` 与 `frontend-design/mygo-fronted` 的对照审计、角色素材 manifest 检查，以及对 Motion / React 当前文档的 Context7 校验

<domain>
## Phase Boundary

本 phase 要解决的是前端体验和组件结构，而不是再改 runtime 边界：

- 以 `frontend-design/mygo-fronted` 为主要模板，把 `apps/web` 的首页、答题、结果体验迁到新的视觉与交互体系
- 保持当前 `apps/api` 内容服务与 `packages/quiz-core` 评分 contract 不变，只重构 `apps/web`
- 把做题流程改成更像 LINE 群聊的消息流，优先复用模板里 `DialogueRow` / `DialogueList` 已有动效
- 把结果页与头像系统接入 8 个角色的圆形头像和 Live2D 静态图插槽，资源来源固定为 `public` 下现有 manifest
- 整个迁移必须按逻辑逐步进行，在 web/api 开发服务器常驻的前提下，每个计划都先浏览器验收，再继续删除旧实现

本 phase 不做：

- 不改 `apps/api` 的只读内容接口、题库版本来源或代理策略
- 不改 `packages/quiz-core` 的角色匹配、tie-break 或隐藏祥子判定
- 不做题库梗化、角色锚点校准或 Phase `3` 的内容深化
- 不做真正的 Live2D runtime 集成；本 phase 只接静态 PNG 资源槽位
- 不新增登录、数据库、CMS、统计后台或分享回流系统

</domain>

<decisions>
## Implementation Decisions

### Locked

- 模板真源固定为 `frontend-design/mygo-fronted`，但运行时代码必须落在 `apps/web`；不能把模板目录直接当生产入口
- 迁移策略必须是渐进式：先搭新壳层与基础设施，再迁聊天答题，再迁结果页，最后才清理旧 `HomePage` 和旧样式
- 当前 `QuizHomeRoute` 的加载、内容读取、答案记录、结果计算与分享导出语义必须先保持一致，避免 UI 改造顺手改坏业务逻辑
- 做题体验的目标形态明确为“像 LINE 群聊一样往下掉消息”，模板中 `DialogueRow.tsx` 的 row entrance、send animation、auto-scroll 机制应优先复用
- 结果页的圆形头像与 Live2D 图槽位必须通过 `apps/web/public/round-icons/manifest.json` 与 `apps/web/public/live2d/manifest.json` 解析，不能把 8 个角色资源硬编码在多个组件里
- 浏览器验收是硬门槛：执行期间保持 `npm run dev:api` 与 `npm run dev:web` 常驻，不允许每做完一个 plan 只靠静态代码审查就继续
- Context7 已确认当前 Motion React 文档使用 `motion/react` 作为 `motion` 与 `AnimatePresence` 的 import 路径；这次迁移动效依赖以该路径为准
- Context7 已确认 React 当前文档仍建议在非阻塞 UI 切换场景使用 transition 语义；因此这次可在 stage 切换、重结果切页等重渲染处选择性使用 transition，而不是把整个状态管理重写

### The agent's Discretion

- `apps/web` 中是否直接引入模板现有 Tailwind 4 基础设施，或先以兼容方式并存接入，只要最终能低风险复用模板组件即可
- 新 UI 是以新 route、子 layout，还是阶段性 feature flag 与旧页并存落地，只要满足渐进迁移和浏览器可回退即可
- 聊天答题流中“返回上一题 / 修改历史答案”的具体交互形态，可以是 inline affordance、底部 action bar 或小型回看面板
- 结果页是否需要增加 dev-only 角色切换预览入口，以便在不重新答题 8 次的情况下逐个验收素材槽位

</decisions>

<specifics>
## Specific Ideas

- 当前 `HomePage.tsx` 把 intro、答题、结果、分享状态都压在一个大组件里；这正是此次要拆掉的迁移阻力
- 模板里已经有 `PageShell`、`PageTransition`、`DialogueRow`、`DialogueList` 等成熟部件，适合先移植基础而不是从零再画一套聊天 UI
- 当前仓库 `band-story` 已经有一版较简化对话组件，可作为 `apps/web` 内部迁移期的桥梁和命名参考
- `apps/web/public/live2d` 与 `round-icons` 已经具备 8 角色资源，不需要再把“等图片”作为阻塞条件；本 phase 应直接把 manifest 变成资源 contract
- 结果页现有数据已经包含 `leadResult`、关系线、榜单、隐藏信号与 share poster，不必改业务字段，只需要换组件结构与素材呈现
- 这次迁移的核心风险不是“功能做不出来”，而是中途把旧链路删早了导致浏览器无法连续验收；因此计划必须强制旧实现并存到新流验收完成

</specifics>
